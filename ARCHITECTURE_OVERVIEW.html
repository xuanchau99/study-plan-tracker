High-Performance System Architecture

Phân tích thiết kế hệ thống QuizMaster qua góc nhìn của Senior Spring Boot Developer

⚡ 1. Xử Lý Chấm Điểm Bất Đồng Bộ (Event-Driven Architecture)

Spring AMQP RabbitMQ Event-Driven Pattern Fire-and-Forget

Hệ thống thi trắc nghiệm thường có đặc thù là lượng người dùng nộp bài cùng một thời điểm rất lớn (ví dụ: khi hết giờ làm bài). Nếu chấm điểm đồng bộ (Synchronous), Database sẽ bị quá tải bởi hàng nghìn câu lệnh SELECT và INSERT cùng lúc, dẫn đến timeout và sập hệ thống.

❌ Cách làm thông thường (Junior)

Nhận request -> Chạy vòng lặp tính điểm -> Truy vấn DB liên tục -> Lưu DB -> Trả về kết quả 200 OK. Connection Pool sẽ bị cạn kiệt ngay lập tức dưới tải cao (High Load).

✅ Thiết kế tối ưu (Senior)

Sử dụng Message Broker (RabbitMQ). Khi nhận request nộp bài, Controller chỉ đóng gói payload thành ExamSubmittedEvent, đẩy vào Queue và lập tức trả về HTTP 202 ACCEPTED. Người dùng không phải chờ đợi. Dưới background, một @RabbitListener (Consumer Worker) sẽ âm thầm pop message ra và tiến hành lấy đáp án từ Redis, chấm điểm, rồi lưu xuống PostgreSQL với tốc độ được kiểm soát, bảo vệ DB khỏi lưu lượng đột biến (Traffic Spike).

🚀 2. Lưu Tự Động Tránh Rớt Mạng (High Throughput Write Caching)

Spring Data Redis Redis Hash Write-Behind Caching (biến thể)

Để đảm bảo không mất bài làm khi rớt mạng, tính năng "Auto-save" yêu cầu mỗi lần click đáp án đều phải gửi request lên server. Nếu có 10,000 học sinh đang làm bài thi 50 câu, hệ thống sẽ phải chịu 500,000 requests ghi vào cơ sở dữ liệu trong thời gian ngắn.

❌ Cách làm thông thường (Junior)

Tạo bảng tạm user_answers trong RDBMS (MySQL/PostgreSQL). Mỗi lần user click, thực hiện lệnh UPDATE/INSERT xuống ổ đĩa cứng. Gây nghẽn Disk I/O trầm trọng.

✅ Thiết kế tối ưu (Senior)

Sử dụng In-Memory Cache (Redis) làm nơi lưu trữ trung gian. Dùng cấu trúc dữ liệu Redis Hash (HSET/HGET) qua StringRedisTemplate.opsForHash() với key là exam:{quizId}:user:{userId}. Việc ghi vào RAM cho phép đạt độ trễ siêu thấp (Low Latency) với độ phức tạp O(1). Chỉ khi nộp bài (submit) thì Worker mới gom toàn bộ đáp án từ Redis xuống PostgreSQL 1 lần duy nhất, giảm thiểu tới 98% thao tác ghi DB.

🛠 3. Lược Đồ Dữ Liệu Động Khắc Phục Anti-Pattern EAV

PostgreSQL JSONB Hibernate 6 @JdbcTypeCode Schema-less Data Model

Câu hỏi trắc nghiệm có cấu trúc rất đa dạng (câu hỏi văn bản, câu hỏi có hình ảnh, câu hỏi có 2 lựa chọn, 4 lựa chọn, hoặc thậm chí là điền khuyết).

❌ Cách làm thông thường (Junior)

Tạo bảng questions (id, text), và bảng options (id, question_id, text, is_correct) rồi nối bảng (JOIN) khổng lồ. Hoặc sử dụng EAV (Entity-Attribute-Value) anti-pattern khiến câu query cực kỳ phức tạp và chậm chạp.

✅ Thiết kế tối ưu (Senior)

Tận dụng khả năng hỗ trợ NoSQL của PostgreSQL thông qua kiểu dữ liệu JSONB. Trong Spring Boot, chỉ cần ánh xạ field details sang một class POJO (chứa options, imageUrl, text...) bằng annotation @JdbcTypeCode(SqlTypes.JSON) của Hibernate 6. Cơ sở dữ liệu vừa được chuẩn hóa tốt, vừa có sự linh hoạt của MongoDB, truy xuất chỉ tốn 1 lần đọc mà không cần JOIN.

🔒 4. Mở Rộng Dễ Dàng Với Stateless Authentication

Spring Security 6 JSON Web Token (JWT) Stateless Session

Hệ thống hiện đại cần sẵn sàng chạy đa máy chủ (Horizontal Scaling) qua Docker/Kubernetes đằng sau một Load Balancer.

❌ Cách làm thông thường (Junior)

Sử dụng mặc định HttpSession của Tomcat để lưu trạng thái đăng nhập. Khi tăng scale lên 3 server, request của user lọt vào server B sẽ bắt đăng nhập lại vì session nằm ở server A (nếu không setup Sticky Session phức tạp).

✅ Thiết kế tối ưu (Senior)

Tắt hoàn toàn cơ chế Session management trong Spring Security (SessionCreationPolicy.STATELESS). Bọc một JwtAuthenticationFilter extends `OncePerRequestFilter`. Xác thực dựa trên Token đính kèm trong HTTP Header Authorization. Các Nodes Backend trở thành thuần API, giúp hệ thống Scale Out (tăng số lượng Container) vô hạn mà không cần đồng bộ trạng thái.

📈 5. Chống Lỗi Kinh Điển N+1 Query Bằng EntityGraph

Spring Data JPA Data Fetching Optimization

Lấy dữ liệu bài thi (Quiz) kèm theo danh sách các câu hỏi (Questions) bên trong nó.

❌ Cách làm thông thường (Junior)

Khai báo @OneToMany(fetch = FetchType.LAZY). Khi gọi API `GET /quizzes/1`, Hibernate thực thi 1 câu lệnh lấy Quiz, sau đó lặp lại thực thi N câu lệnh lấy Question (Lỗi N+1 Query). Hiệu suất giảm thê thảm.

✅ Thiết kế tối ưu (Senior)

Không dùng FetchType.EAGER (gây phình to bộ nhớ). Thay vào đó, sử dụng annotation @EntityGraph(attributePaths = {"questions"}) trực tiếp trên Repository Interface. Hibernate sẽ tự động tối ưu bằng cách tạo một câu lệnh LEFT OUTER JOIN duy nhất xuống cơ sở dữ liệu để kéo tất cả data lên bộ nhớ trong 1 round-trip.

🔔 6. Thông Báo Thời Gian Thực (Push Notification)

Spring WebSocket Native WebSockets Real-time Push

Do hệ thống áp dụng cơ chế chấm điểm bất đồng bộ (chấm ngầm qua RabbitMQ) để giải quyết tình trạng nghẽn cổ chai, người dùng sẽ không nhận được kết quả ngay khi ấn nộp bài. Vậy làm sao để họ biết điểm một cách tự nhiên nhất?

❌ Cách làm thông thường (Junior)

Sử dụng Short Polling: Frontend cài đặt hàm setInterval, cứ mỗi 3 giây lại gửi 1 request GET /api/results để hỏi xem có điểm chưa. Cách này tạo ra hàng nghìn request rác, lãng phí tài nguyên server (CPU, Bandwidth, DB connections) và không thân thiện với pin của thiết bị di động.

✅ Thiết kế tối ưu (Senior)

Sử dụng WebSockets với giao thức STOMP. Server chủ động thiết lập một kênh liên lạc hai chiều mở (full-duplex). Khi RabbitMQ chấm xong, Server tự động đẩy (Push) điểm số qua kênh `/user/queue/notifications`. Bằng cách can thiệp vào vòng đời kết nối qua ChannelInterceptor để xác thực token JWT, hệ thống đảm bảo tính bảo mật và truyền đúng thông báo tới chính xác người dùng mục tiêu với độ trễ gần như bằng không (Zero-latency).

🔥 7. Khả Năng Chịu Tải Thực Tế (Built-in Load Testing)

Stress Test High Concurrency System Resilience

Hệ thống không chỉ được thiết kế trên lý thuyết mà còn được chứng minh thông qua công cụ thử nghiệm chịu tải (Load Tester) tích hợp sẵn, mô phỏng hàng trăm học sinh nộp bài cùng một khoảnh khắc.

❌ Cách test thông thường (Junior)

Mở 2-3 trình duyệt bấm nộp bài bằng tay rồi kết luận hệ thống hoạt động tốt. Khi đưa lên môi trường thực tế (Production), hệ thống ngay lập tức sụp đổ khi có 100 học sinh bấm "Nộp Bài" cùng lúc khi hết giờ.

✅ Thiết kế tối ưu (Senior)

Trang bị sẵn một kịch bản Load Test load_tester.html đính kèm ngay trong ứng dụng Frontend. Bằng cách gọi hàng loạt các bất đồng bộ API tới Backend, nó vắt kiệt sức mạnh của Server. Cách trải nghiệm: Khi hệ thống đang chạy, truy cập http://localhost:5173/load_tester.html. Đặt thử 500 users và nhấn "Bắt Đầu Thực Hiện". Nhờ sự kết hợp hoàn hảo giữa RabbitMQ + Redis + PostgreSQL, bạn sẽ thấy hệ thống trả về HTTP 202 Accepted cho 500 users đó chỉ trong chưa tới 1 giây, sau đó thư thả chấm điểm ngầm và đổ thông báo WebSocket về màn hình Admin mà không hề bị sập!
